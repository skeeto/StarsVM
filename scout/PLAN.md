## D1 — The MessageBox wedge (defect 2). **Highest priority: it makes the whole UI unreachable.**

### Settled root cause

**The investigator's theory was refuted by all three verifiers, and they were right.** The corrected account has two independent halves, and the investigator fused them into one:

**Half A — a real, permanent, guest-driven repaint loop, present from game load.** This is established beyond dispute and is the investigation's genuine contribution. The panel's `WM_PAINT` handler re-lays-out its children; exactly one of the nine `SetWindowPos` calls in the cycle — `SetWindowPos(00C7 0000 00CE 0088 00B6 0050 0014)` at `one-cycle.log:398`, flags 0x14, resize permitted, on an 80px-tall child — is followed by a nested `GetClientRect(parent)` + `FillRect(other DC)` **twice**, i.e. a synchronous `WM_ERASEBKGND` on the parent *inside the parent's own BeginPaint/EndPaint*. The other eight produce nothing. So that child's rect really changes every cycle, the panel is dirty the instant EndPaint returns, and it repaints forever. Verifier 2 measured the period as exactly 593 lines with the mouse physically stationary (all 52 `DefWindowProc(00A8 0200 ...)` carry the identical lParam `017D 02C9`), and verified the healthy and hung cycles are byte-identical with handles stripped.

**Half B — why that survivable loop becomes a hard wedge inside MessageBoxA.** The investigator asserted "MessageBoxA hits the loop before its ShowWindow" with zero citations. The real discriminator, found by verifier 3 and consistent with verifier 2: **the healthy storm is pump-driven, the hung storm is not.** `gameload-region.log:2770-2791` is `EndPaint → GetMessage → WM_NCHITTEST → cursor handler → DispatchMessage → WM_MOUSEMOVE → GetMessage → DispatchMessage → BeginPaint` — two guest `GetMessage` per cycle, so input still flows and the game stays usable (burning a core, which is a separate defect). In the hang, `grep -c "GetMessage\|PeekMessage"` is **0** in `spin-region.log` and `one-cycle.log`, and `msgbox-region.log` has exactly one, at `:166`, *before* the MessageBox at `:188`. After `:188` the guest's pump never runs again. The paints are being driven by a USER32 **synchronous update-region drain** (a `RedrawWindow`/`UpdateWindow`-class flush) that cannot converge because the guest re-dirties inside every WM_PAINT — so the USER32 frame that started it never returns and `ShowWindow` is never reached, which matches the measured symptom (box created, correct rect, foreground, owner disabled, `WS_VISIBLE` clear).

**Definitively not the cause** (all three verifiers agree, and I confirmed the code):
- WM_ENABLE/WM_ACTIVATE/WM_CANCELMODE/WM_KILLFOCUS: each is a single forward that returns, once, not per cycle (`msgbox-region.log:190-194`).
- WM_SETCURSOR/HTERROR: `winproc.c:486-491` is correct (Win16 and Win32 pack it identically); one per cycle in the healthy run too. Pure collateral.
- A non-returning `call16_wndproc`: `thunk.c:194`'s 200M budget is re-armed every dispatch and is structurally unreachable for a callback that returns 2300 times a second. No guard ever fired.

### The change

**The primary fix is already in the tree** (`api_user.c:242`, `dlg.c:149`) and it is the *right* one. **Do not port Wine's `listbox_proc16`.** All three verifiers independently demolished it: Wine's round-up fires only when `(item_height - remaining) <= window_height - client_height`, which for a `WS_BORDER` listbox is a ~2px budget; with any item height of 13-16px the guard is false and it falls through to the same round-DOWN Win32 already does. Wine's own comment calls it "a margin for error," not an anti-oscillation device. It never makes the guest's 80 a fixed point. `LBS_NOINTEGRALHEIGHT` does, which is the only property that terminates the loop. The investigator had this backwards — the "fallback" was always the fix.

**What remains to do, conditional on D0:**

- **If D0 step 1 shows `asked == now` and the BeginPaint storm is gone, and step 2 shows the MessageBox appearing** → D1 is done. Write down the before/after BeginPaint counts and move on.
- **If the storm persists** → the invalidator was never the listbox height. The `[paint]` log at `api_user.c:605-610` and `:1399` will name the actual re-dirtier and the rect. Next suspects, in order: the listbox's own `WS_VSCROLL` scrollbar toggling with content (changes client rect without changing window height, so `NOINTEGRALHEIGHT` would not touch it); a wrong item height for the `LBS_OWNERDRAWFIXED` listbox. Note the loop's listbox is `00B4`/`00C7`, created at `gameload-region.log:591` with style **0x40A00051** = `WS_BORDER|WS_VSCROLL|LBS_OWNERDRAWFIXED|LBS_HASSTRINGS|LBS_NOTIFY` — **not** `:553` (0x40200003, window `00AC`, never in the loop) as the investigator cited. Because it is OWNERDRAWFIXED its item height comes from the **guest's** `WM_MEASUREITEM` reply, marshaled at `winproc.c:367-380` and copied back at `:537-542` (gated on the memcmp at `:615`) — **not** from host font metrics as the investigator claimed. If the height is wrong, the defect is upstream in the font mapping (`SendMessage(00B4 0030 0092)` = WM_SETFONT with guest font 0x92), and a one-line `log_msg` in the `WM_MEASUREITEM` case printing CtlID and itemHeight in/out settles it for free.
- **If the storm is gone but the MessageBox still hangs** → the paint loop was not the wedge. Get a **native stack of the hung thread** (attach a debugger, or breakpoint the panel's WM_PAINT and dump the callstack). That names the USER32 routine in seconds and is worth more than any further trace work. Do not guess.

### Defensive backstop — build it, but trigger it correctly

Every verifier shot down the sketched watchdog, and they were right: a counter of *consecutive WM_PAINT to one hwnd* with a reset on "any other message for that window" **fires in normal gameplay**, because the panel storms from load and the interleaved WM_NCHITTEST/WM_MOUSEMOVE go to a *different* hwnd (`00A8`, not `00AB`). `PAINT_STORM_LIMIT 64` is reached in ~30ms. It would then `ValidateRect(panel, NULL)` forever and leave the message panel stale — reintroducing defect 3's symptom.

**Trigger on the thing that actually discriminates: guest WM_PAINT dispatches with no guest pump in between.** Increment on `WM_PAINT` in `winproc_bridge` (`winproc.c:642`, not `:631`); reset to 0 in `u_GetMessage` / `u_PeekMessage`. In the healthy run this never exceeds 1; in the hung run it climbs without bound. Past a threshold (a few hundred), log **once** — hwnd, class name, and `GetUpdateRect` after the guest returned — and then `ValidateRect(hwnd, NULL)` after each guest return so the synchronous drain converges. Failure mode becomes one stale panel instead of a dead UI.

Also drop the proposed cumulative-instruction budget in `thunk.c`. It would fire in the *healthy* run too — `gameload-region.log` has 136 `GetMessage` calls across 37,451 lines of continuous painting, so "guest burned N instructions without its pump" is this app's normal steady state.

**Files:** `src/winproc.c` (`winproc_bridge`), `src/api_user.c` (`u_GetMessage`/`u_PeekMessage` reset hook). Conditionally `src/winproc.c` WM_MEASUREITEM logging.

**Verify:** MessageBox appears and dismisses, frame re-enabled. `BeginPaint` count in an idle trace drops from 60-per-37k-lines-forever to a handful. Idle CPU is not a pegged core. The watchdog logs nothing during a normal File>Open + 5 minutes of play.

## D2 — Taskbar presence (already landed; three corrections to apply)

### Settled root cause — **confirmed, not refuted**

Both verifiers re-derived it independently and could not break it. The shim passed `0` for `dwExStyle` while faithfully forwarding the guest's `hWndParent`, which for a `WS_POPUP` window is the **owner**. The splash (`starstitle`, `startup.log:678`, style 0x90000000 = `WS_POPUP|WS_VISIBLE`, owner 0x8B) is therefore a visible, owned, non-APPWINDOW popup, which the shell is required to hide. Verified independently: the class-name table decoded byte-for-byte from DGROUP at file offset 723904 (0x196 starsframe … 0x1EA starstitle … 0x20A starstt); exactly 43 CreateWindow calls across the corpus, exactly 2 non-WS_CHILD; the trace-vs-measured style delta of 0x04000000 is USER32 adding WS_CLIPSIBLINGS uniformly, not a post-creation edit; the only `SetWindowLong` offset the guest ever uses is 0xFFFC.

One correction to the investigator's framing that matters for the commit message: **`dwExStyle = 0` was correct code, not a hole.** Win16 has no dwExStyle. This is a deliberate rig-specific deviation from faithful emulation. Label it as such so a future reader does not "fix" it back. The comment currently in the tree does this well.

Verifier 1 also found something everyone missed and it is worth recording: **the frame's taskbar presence is already broken during startup.** The frame is created *without* WS_VISIBLE (0x00CF0000), shown at `startup.log:593`, then **hidden at `:637`** — before the splash exists at `:678` — and not shown again until `:1440`. So today the app has *no* taskbar button at all for ~800 trace lines. That gap is precisely the user's "easy to lose track of it," and the landed fix closes it because the splash now covers the interval the frame vacates.

### Three corrections to the landed code

**(a) Mask the synthetic bits out of `CREATESTRUCT16`.** `winproc.c:313` is `*(uint32_t *)(p + 30) = (uint32_t)cs->dwExStyle;` — the shim rebuilds CREATESTRUCT16 for the guest and copies dwExStyle verbatim. Both target windows demonstrably run guest code with that struct (`startup.log:550` and `:679` are the guest forwarding WM_NCCREATE with a far pointer to it). After the landed fix the guest's WM_NCCREATE handler sees `dwExStyle = 0x00040000` where it has seen 0 for thirty years — and `WS_EX_APPWINDOW` is a bit that did not exist in Win16 at all (Win16 ex-styles stop around 0x20). Nobody can prove Stars! reads the field without disassembling, but it is one line to make the question moot:

```c
*(uint32_t *)(p + 30) = (uint32_t)cs->dwExStyle
                        & ~(uint32_t)(WS_EX_APPWINDOW | WS_EX_TOOLWINDOW);
```

Do this. It is the cheapest risk retirement in the whole plan.

**(b) Narrow the CreateWindow gate to owned windows: add `if (!parent) return 0;`.** `parent` is read at `api_user.c:214` and in scope at `:265`. The frame is unowned and already gets a button (ex=0x00000100 today); `WS_EX_APPWINDOW` is only *needed* when a window is owned. Narrowing leaves the frame's ex-style bit-identical to what shipped, i.e. zero regression surface on the one top-level window that was already correct — and it makes the unverifiable `starspopup`/`starstt` deny-list unnecessary, because an owned transient stays suppressed exactly as it is today. This is the right answer to the open question about the four never-traced classes: instead of guessing from class names, let them fall through the same rule as everything else. **Do not add a `WS_EX_TOOLWINDOW` deny-list** — TOOLWINDOW on a captioned popup gives it the short tool caption, changing the client rect for a given window rect and therefore the WM_SIZE/GetClientRect numbers the guest lays out against. That is a silent geometry regression on windows no trace has ever shown us, in exchange for nothing.

**(c) Reconsider the dialog half at `dlg.c:112`.** I parsed this myself: **all 36 RT_DIALOG templates have full WS_CAPTION (0x00C00000), none is WS_CHILD, none sets DS_CONTROL.** The caption gate as written is **provably dead code** — it returns `WS_EX_APPWINDOW` for 36 of 36. The stated effect ("only suppresses caption-less or DS_CONTROL panels") describes an empty set. The real, unstated effect is that **every dialog type in the game gets a taskbar button and an Alt-Tab slot**, appearing and vanishing on essentially every click of a game whose entire interaction model is modal dialogs. The brief explicitly asked for buttons "without polluting Alt-Tab."

Decision: **the dialog half is mostly unnecessary and should be narrowed or reverted.** Windows already redirects a taskbar-button activation of a disabled owner to its last-active popup, so a modal dialog owned by the *visible frame* is already reachable through the frame's button. The only genuinely unreachable dialog is the startup wizard, owned by the **splash** (`startup.log:820`, parent=009D, template #209, style 0x90C800C0) — and giving the splash a button (which (b) preserves) makes that reachable too.

If you keep the dialog half, replace the inert caption test with the one bit that actually partitions this binary: `WS_SYSMENU`. Template styles, straight from the resource table: 31× 0x90C800C0, ord 91/92 0x80C800C0, ord 90/97 0x00C800C0, **ord 393 0x90C000C0**. Ord 393 is the only one without WS_SYSMENU — one control, captioned, WS_POPUP|WS_VISIBLE: the shape of a transient wait/status box, which would otherwise get an Alt-Tab slot with **no close affordance**. `WS_SYSMENU` excludes exactly that and nothing else; `WS_CAPTION` excludes nothing.

My recommendation, in order: revert `dlg.c:112` to `0`; ship (a)+(b); look at the result. Add the dialog half back, gated on `WS_SYSMENU` **and** `parent != 0`, only if a specific dialog is demonstrated unfindable with the splash buttoned.

**Corrections to the investigation for the record:** de-owning the splash was asked about and never answered — the answer is **no, strictly worse**: `startup.log:1425-1434` shows `DestroyWindow(009D)` followed by `WM_ACTIVATE` on 009D and `WM_ACTIVATEAPP` handed back up to the frame 008B; clearing the owner changes who receives that activation, drops destroy-with-owner and guaranteed z-order, and changes `HWND_16(cs->hwndParent)` in the guest's own CREATESTRUCT16 from 008B to 0000. `WS_EX_APPWINDOW` leaves the owner relationship intact, so z-order and owner-disabling are unchanged. `ITaskbarList::AddTab/DeleteTab` does exist as a reversible post-creation mechanism (so the investigator's "there is no post-creation window" is overstated — `dlg.c:260-267` itself exploits a pre-visible moment for the four templates lacking WS_VISIBLE), but it needs COM init on the pump thread and suppression turns out to be unnecessary: the splash is destroyed before the frame is shown in both traced runs.

**Files:** `src/winproc.c` (line 313 mask), `src/api_user.c` (line 249 gate), `src/dlg.c` (line 112).

**Verify:** Start the game. A "Stars!" taskbar button exists continuously from the splash through the frame — including the `:637`-to-`:1440` gap that had none. Alt-Tab shows one entry, not one per dialog. Open and close five dialogs: no button churn. Guest `dwExStyle` in CREATESTRUCT16 reads 0 (log it once).

## D3 — The missing bottom-left message panel on New Game (defect 3)

### The investigator's root cause is REFUTED. All three verifiers demolished it independently, and the evidence is unambiguous.

**What the investigator claimed:** the panel's children are shown only by its WM_SIZE handler, fed by one size-changing MoveWindow that never lands on New Game; fix by synthesizing WM_SIZE/WM_MOVE on a top-level window's hidden→visible edge in `u_ShowWindow`.

**Why that is wrong, on four independent counts:**

1. **The panel's buttons are made visible during `CreateWindow`, on every path.** `gameload-region.log:681-728` is a single CreateWindow call — the `WM_PARENTNOTIFY(wParam=WM_CREATE, child=00C6)` forwarded to the frame at `:727` can only be sent from inside CreateWindow, and `:725/:726/:727/:728` (WM_SIZE 10x10, WM_MOVE -500,-500, WM_PARENTNOTIFY, WM_SHOWWINDOW) is the textbook CreateWindowEx tail, identical to the toolbar's at `:675-678`. So the `SWP_SHOWWINDOW` burst at `:717-724` is the panel's **creation-time** layout, and the buttons get WS_VISIBLE then. The later pass at `:772-774` is `SWP_NOSIZE|SWP_SHOWWINDOW` on already-visible windows: it only **moves** them (x −38 → 348, right-aligned to a 396px client). Visibility is not what is missing; placement is.
2. **"The frame caches its client size from its WM_SIZE" is false.** `grep -c "DefWindowProc(008B 0005"` is **0 across all six logs**, and `frame-msg-histogram.txt` has no 0005 row. The frame has never been observed to receive WM_SIZE at all.
3. **The layout routine is not message-driven on the path that works.** `gameload-region.log:729` (`IsIconic(008B)`, first call of the routine) is the line immediately after `:728`, with no dispatch between — the caller of `CreateWindow(00C6)` invokes it directly on return. Same at `:913`, directly after a `SetWindowPos`. Only the third pass (`:1283`) follows a `DispatchMessage`. Whatever `ShowWindow` did or didn't send is irrelevant to it.
4. **The proposed fix is inert on the path it targets.** On New Game, `ShowWindow(008B, SW_SHOW)` is `startup.log:1440`. There is **no `USER.41 CreateWindow` anywhere after it** through end of log at `:1500` — the universe is still being GlobalAlloc'd at `:1484-1495`. A synthesized WM_SIZE there runs the layout routine on a childless frame: exactly the no-op already visible at `startup.log:629-635`. And `gameload-region.log:944-978` proves the premise anyway — on the **working** path, `ShowWindow(008B 0005)` produces no WM_MOVE and no WM_SIZE either, byte-for-byte the same shape, and the panel comes up correctly.

Additionally the fix's `!(style & WS_CHILD)` guard does not exclude popups or dialogs, so the splash, every DialogBox and every MessageBox would start receiving a synthetic WM_SIZE re-entering the guest from inside `USER.42` — on the same files where D1's MessageBox hang lives.

### Corrected theory (medium confidence, and say so)

One routine — call it `LayoutFrame` — does `IsIconic(008B); MoveWindow(toolbar); MoveWindow(scanner); MoveWindow(planet); MoveWindow(panel); MoveWindow(00A9); GetMenu(008B); GetSubMenu ×2; CheckMenuItem ×3`. Note the tail: it is a **combined "reposition the panes AND re-sync the menu check marks"** routine. That is the mechanical link to the user's clue. All five panes are created degenerate at (−500,−500) 10x10 and are positioned by nothing else (MoveWindow count = 3 for each of the five, SetWindowPos count = 0).

Two candidates, both consistent with the symptom being **selective** (one pane missing, rest of UI fine — which by itself refutes "LayoutFrame never ran," since that would leave the scanner, planet pane and toolbar all off-screen too):

- **(a) Guest control flow.** New Game's completion routine simply does not make the direct `LayoutFrame` call that `gameload:913` makes; the first `WM_INITMENU` from clicking File runs the composite routine and everything snaps into place. The guest handles WM_INITMENU itself — it never forwards one (no 0x0116 anywhere in the histograms) — so this is entirely guest-side and needs no shim change at all.
- **(b) The one layout pass runs before the panel exists.** The guest's stored pane handle is still 0, `MoveWindow(0000, 0, 850, 396, 110)` fails silently (`u_MoveWindow` discards the BOOL), the other four land, and the panel is left 10x10 at (−500,−500) with its buttons clipped away — which matches "the buttons really aren't there" better than (a) does.

Both are selective. Both predict the same instrumentation signal.

### The change

**No bridge change yet. Instrument and capture a New Game trace** — no existing trace covers the New Game path past universe generation, which is the single most valuable missing artifact in the whole set. Log, in `api_user.c`:

- every `USER.41 CreateWindow` with class name, resulting hwnd, parent, style;
- **all five** `MoveWindow`/`SetWindowPos` calls with hwnd, rect, and BOOL result — not just failures, and log loudly when `hwnd != 0` but `HWND_32(hwnd)` is NULL;
- a marker on entry to the `IsIconic(008B)` burst (easiest: log every `USER.31 IsIconic`).

Then run New Game to the first turn and answer: **after `CreateWindow(starsmessage)` returns, does the layout burst occur at all, and with how many panes?**

- Burst absent until a menu is opened → theory (a), guest control flow, **no shim fix is warranted**. Document it as a faithful-emulation artifact or find what host-side difference changes the guest's path (most likely candidate: a `WM_COMMAND` the File>Open path posts — `gameload:793`, `:1051` — that New Game does not).
- Burst runs with four panes / a `MoveWindow(0000, ...)` → theory (b). The repair is to make the guest reach the panel, which means finding why its handle is still 0 — again guest-side ordering, not `u_ShowWindow`.

**Log the BOOL from `u_MoveWindow`/`u_SetWindowPos` permanently regardless.** A silent false return on a five-call layout routine is exactly the class of bug that should never again cost a week.

**Do not ship the `u_ShowWindow` WM_SIZE synthesis.** If a later measurement genuinely shows a missing first-visible WM_SIZE, revisit — but gate it on `!(style & WS_CHILD) && !(style & WS_POPUP)` and on it being the window's *first* show (Win16's `WIN_NEED_SIZE` is a one-shot creation flag; the frame's genuine first show at `startup.log:593` already produced WM_SIZE+WM_MOVE, so the shows at `:1440`/`:944` are second shows and Win16 would not have re-sent anything either).

**Files:** `src/api_user.c` (logging only, at this stage).

**Verify:** New Game to turn 1; the panel appears at (0, 850) 396x110 with Prev/Goto/Next at x=348 without touching a menu.

## D4 — `u_DefWindowProc` returns a raw 32-bit host handle where a 16-bit one is expected (WM_CTLCOLOR). **Live on the main screen today.**

Promoted above the remaining latent items because the trace proves the path is hot and the symptom is visible pixels.

`api_user.c:319-322` returns `winproc_default()`'s `LRESULT` verbatim to the guest as DX:AX. `winproc.c:489` sets `x->ret_handle = H_BRUSH` for all seven `WM_CTLCOLOR*`. So when the guest just forwards, `winproc_bridge` (`winproc.c:674`) takes the **low word of a real HBRUSH pointer** and runs it through `winproc_ret_handle` → `h32_quiet(H_BRUSH, ...)` → NULL — or, once the handle table has grown past that index, a **different, real brush of the right type**.

Trace-confirmed hot: `gameload-region.log:19, 792, 816, 1367, 2618` are `DefWindowProc(009D 0019 ... 0003 00Ax)` — WM_CTLCOLOR with `CTLCOLOR_BTN`, on the four real Win32 buttons created at `startup.log:704/707/710/714`.

**Change:** on the `u_DefWindowProc` side, when the in-flight message has a handle-valued return, map it: `return h16(H_BRUSH, r)` (and the same for any other `ret_handle` type). Do **not** change `winproc_ret_handle`, which is correct for values the guest actually produced. Same hole, same shape, at `api_user.c:1055-1058` in `u_CallWindowProc`'s wrapped-host-proc branch.

**Symptom it fixes:** wrong or unpainted background behind command buttons and static text, changing over a session as the handle table deepens.

**Verify:** button backgrounds correct on the splash and in dialogs; log the returned brush handle once and confirm it is a 16-bit value ≥ 0x40.

## D5 — `LB_GETSELITEMS` writes host DWORDs to a guest SEGPTR. **Merge Fleets crashes.**

`msg16.c` has no case for `LB_GETSELITEMS` (Win16 0x0412 → Win32 0x0191) or `LB_GETSELCOUNT`, and neither is on the `refuse` list (`msg16.c:236`), so the far pointer is forwarded raw and USER32 writes `count` **32-bit** ints (Win16's array is **16-bit**) to the numeric value of the SEGPTR — roughly 21 MB into the address space.

Reachable in ordinary play: template 82, `caption='Merge Fleets'`, `LISTBOX id=81 style=50A10009` — `LBS_MULTIPLESEL|LBS_NOTIFY`, the **only** multi-select list in the game.

**Change:** add an `OUT_*` case that allocates a host `int[]`, calls through, and writes the results back as 16-bit words into the guest array. At minimum, add both messages to the `refuse` list so it fails loudly instead of corrupting memory.

**Verify:** select two fleets in Merge Fleets, hit OK. No crash; the right fleets merge.

## D6 — `EM_SETSEL` parameters are in different places in Win16 and Win32

No `case EM_SETSEL` in `msg16.c`'s `marshal_in`. The renumbering at `msg16.c:25-27` correctly maps Win16 0x0401 → Win32 0x00B1 for an `Edit`, then forwards wp/lp verbatim. Win16: `wParam` = scroll flag, `LOWORD(lParam)` = start, `HIWORD(lParam)` = end. Win32: `wParam` = start, `lParam` = end. So `EM_SETSEL(0, MAKELONG(4,9))` arrives as start=0, end=589828 — every selection collapses to "from 0 to the end."

Affects the 13 EDIT controls in the shipped templates: Ship & Starbase Designer design name (id=2075), Rename Battle Plan, Find Planet or Fleet, Change Password ×2, Print Map page counts, Serial Number. "Place the caret at N" and "select the bad digits" both select the whole field, so the next keystroke wipes it.

**Change:** `case EM_SETSEL: m->wp = LOWORD(m->lp); m->lp = HIWORD(m->lp); break;` after renumbering. `EM_GETSEL` and `CB_SETEDITSEL` are identical in both and need nothing. `EM_LINESCROLL` also differs but is dead here — no template carries `ES_MULTILINE`.

**Verify:** open Ship Designer, observe the default name is selected; type a character and confirm only the selection is replaced.

## D7 — `WM_MENUSELECT` / `WM_MENUCHAR` have their lParam halves swapped

`winproc.c:442-450` writes `MAKELONG(HMENU_16(lp), HIWORD(wp))`. The Win16 contract for both is **`LOWORD(lParam)` = flags, `HIWORD(lParam)` = HMENU** — exactly inverted. (The neighbouring `WM_HSCROLL` case at `:437` gets its own swap right, and `WM_ACTIVATE` at `:452` puts the handle in the high word correctly; these two were written as if they had WM_COMMAND's layout.) Secondary: in Win32 `LOWORD(wParam)` is a *position index* when `HIWORD(wParam) & MF_POPUP`, where Win16 had the submenu HMENU.

Consequence: any `MF_GRAYED`/`MF_POPUP` test reads handle bits, so the branch taken is effectively random.

**Change:** `x->lp16 = MAKELONG(HIWORD(wp), HMENU_16((HMENU)lp));` in both cases.

**Confidence it is currently reached: low** — 0x011F never appears in any histogram, but no scout region covers menu navigation, so that is non-evidence. The neighbouring `WM_INITMENUPOPUP` path *is* live (26 `CheckMenuItem` + 17 `EnableMenuItem`) and is correct. Fix it anyway: it is two lines and unambiguously wrong.

**Verify:** hover the menu bar with a status-hint breakpoint, or simply confirm no regression.

## D8 — `SetWindowLong(GWL_WNDPROC)` can install a wrapped *host* proc as guest code

`api_user.c:1019-1029` stores `val` unconditionally, where `u_CallWindowProc` (`:1045`) carefully calls `winproc_to_host(proc)` first. The standard un-subclass idiom — `SetWindowLong(h, GWL_WNDPROC, oldProc)` with the value this same function handed out — stores a pointer into `hostproc_sel`, a bare `sel_alloc(0x1000, SK_CODE)` with **no code in it** (`winproc.c:45-48`). The next message runs `call16_wndproc` into 4 KB of zeroes, burns the 200M budget, logs "ran away," and latches a fatal fault: the app freezes for a long moment and dies.

The game does subclass — `gameload-region.log:576-577, 670-674` show `GetWindowLong(... FFFC)` / `SetWindowLong(... FFFC ...)` on three windows during File>Open. In those three cases `winproc_get(hwnd)` is non-zero (they are the game's own classes), so the round-tripped value is a guest SEGPTR and safe. **The trap springs only on a stock control.**

**Change:**
```c
if (off == GWL_WNDPROC) {
    WNDPROC host = winproc_to_host(val);
    if (host) { SetWindowLongPtrA(hwnd, GWLP_WNDPROC, (LONG_PTR)host);
                winproc_forget(hwnd); return prev ? prev : winproc_from_host(host_prev); }
    ...
}
```

**Interaction with D1:** if you ever add a host subclass on stock listboxes (you should not — see D1), this becomes load-bearing rather than latent.

## D9 — Polish and latent items, in descending value

- **`msg16_to_32()` (`winproc.c:192-197`) is class-blind and its second branch is unreachable.** `if (msg >= 0x0400 && msg <= 0x040F) return msg - 0x0310;` already returned, so the `<= 0x042F` line can never fire for the first range; `LB_*`/`CB_*`/`SBM_*` are unhandled. Three callers: `api_user.c:325` and `:1057` (the non-in-flight fallbacks), and `get_msg16` at `:371`, which pairs with `put_msg16` at `:356` and **is not an involution** — a posted `EM_*` or `SBM_*` is written to the guest as 0x0400..0x040F and read back as 0x00F0..0x00FF, arriving at `DispatchMessage` as a **`BM_*` message**. Compounding it, `api_user.c:358` truncates `wParam` to 16 bits with no way to recover it. Latent (only 6 `PostMessage` calls in the whole corpus, and `u_PostMessage` → `msg16_post` converts before queueing), but it is a landmine. Either delete `msg16_to_32` in favour of `msg16.c`'s class-aware `msg16_to_32_for`, or make the pair a genuine round trip by stashing the original 32-bit msg/wParam alongside the queued message.
- **`WM_SETTEXT` / `WM_GETTEXT` reach the guest with a raw host pointer.** `gameload-region.log:517`: `DefWindowProc(008B 000C 0000 00DF E8F0)` — a host stack pointer in a 16-bit lParam. Survives only because the guest forwards and `winproc_original` substitutes. Same on the read side: `u_GetWindowText` calls `GetWindowTextA` on a same-process window, which USER32 implements by **sending WM_GETTEXT** to `winproc_bridge`. Breaks the moment any guest class handles its own text. Add in/out string marshaling.
- **`WM_ENTERIDLE` hands the guest a 32-bit HWND in lParam.** `gameload-region.log:1-5`: `DefWindowProc(009D 0121 0000 0026 10EC)`. One line: `x->lp16 = HWND_16((HWND)lp);`.
- **`WM_COMPAREITEM` is promised by the `winproc.c:13-15` header comment and absent from the table.** Currently dead — none of the 6 LISTBOXes or 10 COMBOBOXes in the 36 templates sets `LBS_SORT`/`CBS_SORT`. Add it, or delete it from the comment.
- **Combo boxes get no `CBS_NOINTEGRALHEIGHT`.** The listbox accommodation now exists at `api_user.c:242` and `dlg.c:149`; neither covers `CBS_NOINTEGRALHEIGHT (0x0400)` on class ordinal `0x85`, and there are ten COMBOBOXes with 55-95 DLU dropped heights (New Game race picker, the id=1054..1058 selectors). **This interacts directly with D1** — if the paint storm survives the listbox fix, a combo box doing the same oscillation is the next suspect. Also note `dlg.c:149` matches only the one-byte ordinal form; fine today (all 36 templates use ordinals) but fragile.
- **`WM_GETFONT` has no `ret_handle`.** `msg16.c:160-162` maps the outbound result through `h16(H_FONT, ...)`, but `msg_to_16` never sets `x->ret_handle = H_FONT` inbound (it does handle `WM_SETFONT` at `winproc.c:509`). Asymmetric by inspection; low reachability.
- **`BACK_NCCALC` copies back only `rgrc[0]`** (`winproc.c:565-571`) though `msg_to_16` hands the guest all three. A guest returning `WVR_VALIDRECTS` gets `rgrc[1]`/`rgrc[2]` discarded → smeared client content while dragging a panel edge. Low likelihood.
- **`inflight_push` can be skipped while `inflight_pop` still decrements.** `winproc.c:222` returns silently at `MAX_INFLIGHT 32`; `:231`'s pop is unconditional, so the top drifts and a later push overwrites a live outer frame — `winproc_original` could then hand DefWindowProc another message's parameters. Narrow window (`thunk.c:135` latches a fatal fault at the same depth), but the fix is trivial: have `inflight_push` return whether it pushed and pop only then.
- **Handle slots are never reused.** `handle.c:27` `next_free` only increments; `h_release` clears the entry but not the counter and is called for only three things. At `MAX_HANDLES 8192`, `h16` starts returning 0 and every handle silently becomes NULL. Partly self-limiting (dedup on host pointer, Win32 recycles HWND/HDC values). Add a high-water-mark counter to the log so a long game reveals whether this is real.
- **Icon polish.** The class icon has landed. Two follow-ups: (i) `stars16.manifest` sets `dpiAware false`, so `SM_CXICON`/`SM_CXSMICON` are frozen at 96-dpi 32/16 for the process life — `icon_app16(32,32)` is therefore a 1:1 copy of a resource that IS 32x32, and only the small icon is ever a scale; but the trace shows WM_GETICON arriving with `lParam = 0x0090 = 144` (`startup.log:658, 665, 737`), i.e. Windows asking for a 150%-scaled caption, so consider building the big icon at 48 or 64 for sharpness. (ii) The module ships **no 16x16 image** — all ten RT_ICONs are 32x32 4bpp, 744 bytes — so a hand-drawn 16x16 member is new art, a user decision, not an extraction. (iii) **Do not add `WM_GETICON` to `msg_to_16`'s `ret_handle` table next to `WM_QUERYDRAGICON` at `winproc.c:513`** — it looks like an obvious tidy-up, but it would push a genuine host HICON through `h32_quiet` and hand the shell garbage. Put a comment there saying so.
- **`stars16.ico` is artwork from a commercial game.** If this repo is or becomes public, either move to build-time extraction (accepting that a source-only clone cannot build without `GAME=`) or ship original art. User's call.

## INTERACTIONS AND MASKING — read before sequencing

1. **D1 ↔ D3 (the big one).** The landed listbox fix's own comment claims it explains the missing panel: *"a window that is always dirty always wins the paint queue, every other window starves and is never drawn at all — which is why the turn-summary panel was missing."* **That claim is unproven and probably wrong** — the panel is missing on *New Game*, and defect 3's evidence shows the panel is created 10x10 at (−500,−500) and never repositioned, which is a geometry failure, not a starvation failure. If D0 step 3 shows the panel now appearing on New Game, **do not conclude the listbox fix caused it** without checking the `MoveWindow(00C6, 0, 850, 396, 110)` log line: the panel could be appearing because it is finally *painted*, or because the layout pass finally *ran*, and only the log distinguishes them. This is the single most likely place in the whole plan to declare victory on a coincidence.
2. **D1's watchdog can mask D1's root cause.** `ValidateRect` after a storm converts a hang into a stale panel. If you ship the watchdog before confirming the storm is dead, you will never again see the storm in a trace. **Land the watchdog last within D1, with its one-shot log line, and check that the log is silent in normal play.**
3. **D1's watchdog can mask D3.** A watchdog that misfires on the panel (as the sketched consecutive-paint version provably would) leaves the panel stale — reproducing defect 3's exact symptom on the *working* path. This is why the trigger must be "paints since last guest pump," not "consecutive paints."
4. **D2 ↔ D1, same files.** `api_user.c:249/260` (taskbar) and `api_user.c:242` (listbox) are eleven lines apart in `u_CreateWindow`; `winproc.c:313` (D2's mask) and `winproc_bridge` (D1's watchdog) are in the same file. Do D2's three corrections in one small commit *before* starting D1's watchdog, so the diffs do not overlap.
5. **D2's dialog half ↔ D1.** A MessageBox is built by USER32 itself and never passes through `dlg.c`, so `dlg.c:112` cannot affect defect 2 either way. But if you revert `dlg.c:112` while D1 is unresolved, do not let the reverted line confuse the msgbox investigation — they are unrelated.
6. **D4 ↔ D8.** Both live in the GWL/DefWindowProc handle-translation area of `api_user.c` (lines 319-325, 1019-1058). Do them in one commit.
7. **D9's combo-box item is D1's plan B.** If the listbox fix does not kill the storm, check the combo boxes before anything else.
8. **Everything touching `u_CreateWindow` is now crowded.** `api_user.c:204-274` currently carries the listbox quirk, the taskbar ex-style, and the menu/id disambiguation. Any further additions there want a comment block, not another inline `if`.
